EXECUTIVE SUMMARY

This study is aimed at those responsible who wish to use hash techniques in their processing as a guarantee of pseudonymization of personal data. Throughout the text, the fundamentals of hash techniques and their properties are introduced. In the application of these techniques, in some cases, there is a high risk of identifying the message that generated the hash. The document analyzes the sources of reidentification risk in the application of hash techniques and establishes the need to conduct an objective analysis of these risks to determine the suitability of this as a technique for pseudonymization or even anonymization. This analysis involves both the process employed and the other elements that make up the hash system, with particular attention to the entropy of the messages and the information linked or linkable to the value represented by the hash.

I. INTRODUCTION AND OBJECTIVE OF THE STUDY
The value of data is currently indisputable. Data has become a key factor for scientific research, public administration, and a growing digital economy. The development of promising technologies such as Big Data or Machine Learning largely depends on the amount of data that can be provided to them. This growing demand for personal data has led to renewed interest in anonymization processes and techniques. Hash functions have long been used to provide additional protection in the processing of personal data. However, there are doubts about the extent to which hash is an effective technique for pseudonymization and whether, under certain circumstances, such as when the original message has been deleted, it can even be considered that the value of the hash is anonymized. This decision is of paramount importance to determine, among other things, the effective compliance with the rights established in the GDPR in certain types of processing, such as in research, traffic data analysis, geolocation, blockchain, and others. When making this decision, legal, technical, and process management considerations come into play, so those involved need to have a basic understanding of hash techniques and their potential risks. This study is directed at those responsible for processing who wish to use implementations based on the use of hash functions to pseudonymize or anonymize personal data. It briefly presents the fundamentals of hash functions, their properties, the possibilities of reidentifying the message that generated the hash, and establishes certain guidelines for analyzing the suitability of a treatment that uses hash functions.

II. HASH FUNCTION
A hash function is a process that transforms any arbitrary set of data into a new series of characters with a fixed length, regardless of the size of the input data. The result obtained is called a hash, digest, or image. Often, the term "hash" is used both to refer to the hash function and to the resulting value of executing that function on a particular message. The data that will be processed by the hash function is called a message or preimage. The set of all possible messages or preimages is the domain or message space. DESIRABLE PROPERTIES IN A HASH FUNCTION  
The ideal properties of a hash function are:  
• It allows execution on digital content of any size and format. In the end, all digital content is numbers for the computer: texts, photographs, videos, etc.  
• Given any input, it produces a fixed-size numerical output.  
• The result is deterministic, meaning that for the same message or set of input data, the same result is always obtained.  
• Reconstructing the original message from the hash function result must be extremely costly, if not impossible.  
• A minimal variation in the original message (one bit) must produce a completely different hash (avalanche effect).  
• If an input message is selected, finding another message that has the same hash must be extremely costly (weak collision).  
• It must also be extremely costly to find any two messages that have the same hash (strong collision).  
• The hash algorithm must uniformly cover the entire hash space, which means that any result of the hash function has, a priori, the same probability of occurrence as any other. Therefore, all values in the hash space can be the result of the hash function.  
DESCRIPTION OF A HASH FUNCTION  
In general, a hash function works as follows:  
• The input message is divided into blocks.  
• A formula calculates the hash, a fixed-size value, for the first block.  
• The hash of the next block is calculated and added to the previous result.  
• The same process is repeated until all blocks have been processed.

III.  
HASH AS A UNIQUE IDENTIFIER  
The number of possible results of a hash function is very high, but not infinite. Since the message space can be infinite, there will be infinite messages that can yield the same hash value. The set of messages that result in the same hash value is called the preimage set.

ANALYSIS BASED ON A SPECIFIC TREATMENT  
Let us suppose that a treatment wants to associate a hash value with each of the books that have been published in the world, based on the digitization of their contents. A few years ago, Google published that the number of books published in the world was 130 million13.

The difference between the set of published books and the rest of the possible messages that could be a preimage of El Quijote lies in the concept of "order." Books are not formed by any combination of letters, but rather by words of a specific language, forming sentences with a particular syntax, with a narrative structure, and expressing a meaningful message. Therefore, if a meaningless message had the same hash as that corresponding to a specific book, we would discard it as belonging to our effective space of messages, that is, as belonging to our processing.  
The stricter that "order" is, for example, in the case where only books in Spanish are allowed and not in any language, the smaller the set of books (the message space of my processing) will be, and there will be less probability of collision. Even so, nothing guarantees that two hash values corresponding to two different books do not match, although the probability is indeed very low in a well-constructed algorithm, and this possibility can be determined analytically through a generalization of the birthday paradox. Therefore, if we were to represent within the space of hashes a diagram that contains all the hashes corresponding to the real message space, it would have a diffuse limit, that is, if there are a trillion published books and their hashes are generated, it is highly probable that a trillion distinct hashes will be generated, but it is not guaranteed, although, for practical purposes, the correspondence between books and hashes is one-to-one, bijective.  
IV.  
REIDENTIFICATION PROBLEM  
Hash functions aim to be irreversible (see their desirable properties), and therefore the result of applying a hash function to a direct identifier should prevent its reidentification. Nevertheless, the same "order" that is implicit in a processing and that guarantees the effectiveness of the hash as a unique identifier also increases the probability of identifying the original message from the hash.  
PROCESSING OF PHONE NUMBER HASH  
As an example, let us suppose that in a processing the hash of a mobile phone number from a telecommunications company is evaluated. The designer of the processing uses a hash function that generates a hash value of size 64 bits.  
A mobile phone number consists of 9 digits, plus two for the area code and preceded by the symbol "+", totaling 12 symbols. If each symbol is stored in one byte, the total number of bits is equal to: 12*8 = 96 bits.  

In the previous figure, it is represented how the space of phone numbers is greater than the space of hashes. If all possible hashes for all combinations of 96 bits were calculated, inevitably the entire hash space would be covered, resulting in more than four billion collisions. In principle, the hash function would have to "compress" the 96 bits of the number into the 64 bits of the hash.  
On one hand, if the 96 bits of the number contained information, converting that number to a 64-bit hash would necessarily lose information and make the hash irreversible. On the other hand, one might wonder whether such a design of the processing meets the requirement of having a unique identifier.  
ANALYSIS OF THE PROCESSING  
A more detailed analysis would answer these questions:  
• On one hand, eleven of the digits are numeric, which implies 100 billion combinations. If we assume that there are only 20 possible symbols on a keyboard, the encoding of an additional symbol to register the initial "+" would increase the number of combinations to 2 trillion. It seems like a very high number, but if we translate it to bits, we have reduced the amount of data from 96 bits to approximately 41 bits. That is, much less than the initial 96 and already below the 64 bits of the hash size, therefore, it would be useful as a unique identifier.  
• As the framework of the processing assumes that all numbers are from Spanish subscribers, it is known that the prefix +34 is common, therefore, this data is fixed and with the remaining 9 digits there are one billion combinations (approximately 30 bits).  
• If Spanish mobile phone numbers are being processed, they will start with 6 or 7. Therefore, with the first digit fixed, there are only 200 million combinations (approximately 28 bits).  
• But there are not 200 million subscribers in Spain. The current number of mobile lines does not reach 60 million (26 bits).  
• The operator with the most mobile lines does not reach 20 million (20 bits of information), therefore, if the mobile operator to which the hash of the number corresponds is known, and access to the list of numbers is available, the number of combinations decreases enormously, and the actual information contained in the original 96 data bits is only 20 bits of information.

As the example shows, in the definition of processing there is an implicit order that limits the set of possible messages within that processing (its message space). The number of valid possible messages (220) is much lower than the number of possible hashes (264), which means the possibility of collision is very low17 and the hash would practically behave as a unique identifier.  
ANALYSIS OF REIDENTIFICATION  
Regarding the possibility of determining the number corresponding to a given hash, considering that a desktop computer can calculate more than 1 million hashes per second, it is possible to create a dictionary for all possible hashes of the phones of a given operator in less than 20 seconds, practically in real time18. That is to say, the information referenced by the hash can be recovered.  
In this case, the amount of information was small, but even for much larger message spaces, with more information, there are known techniques such as Rainbow Tables19 that allow for the reversibility of the hash.  
ORDER, DISORDER, AND INFORMATION  
When the data used in a processing has an implicit order, the set of possible messages (message space) is greatly reduced, which facilitates the reversibility of the messages (reidentification).  
The greater the implicit order in a dataset, the more determined the message is, and the less real information it contains. Knowledge derives from the very structure of the data (e.g., Spanish mobile phone numbers start with +346 or +347) or knowledge about the processing environment (e.g., the phone numbers managed by an operator are known). For all these reasons, it is necessary to distinguish between the data of a message (96 bits in the previous example) and the information contained in that data (20 bits in the previous example).

The degree of order, rather disorder, of a set of data is known as entropy. The greater the entropy, the more information a set of data will contain. Conversely, less disorder (less entropy) implies the existence of fewer alternatives, and therefore the same data will contain less information.  
The smaller the message space, and the lower the entropy, the lower the risk of collision in hash processing, but re-identification will be more likely. Conversely, with greater entropy, the possibility of a collision will be higher, but the risk of re-identification will be lower.  
The measure of the amount of information, which is very different from the number of bits being used to record a message, is one of the most important analyses to be carried out whenever there is an intention to protect a message, whether through hashes or using other techniques such as encryption, and requires rigorous analysis.  
V.  
LINKING INFORMATION TO THE HASH  
In the case of the previous chapter, the more information available from the potential message space (its structure, the geographical location of users, the company to which they belonged), the greater the "order" implicit in the message and the less information the hash itself contained, making its re-identification more likely.  
IDENTIFIERS LINKED TO THE HASH  
A file with personal data may contain "identifiers" that are uniquely associated with an individual (e.g., ID number, full name, or passport).  
If there are identifiers linked to a hash, for example, if the ID number and the hash of a phone number associated with that ID number are stored, it is evident that the information belongs to a specific individual. Regarding the confidentiality of the information represented in the hash, having a linked identifier will add an additional vulnerability to the weakness of the hash in question, as information from the ID number could be used to reduce the effective message space for that specific hash.  
That is to say, the more personal information linked to the hash, the greater the risk of identifying the content of the hash.  
PSEUDOIDENTIFIERS LINKED TO THE HASH  
Files with personal data may also contain other data that, when appropriately grouped and cross-referenced with other sources of information, can lead to the identification of an individual. These data are referred to as "pseudo-identifiers," "quasi-identifiers," or indirect identifiers. The relationship between these and the hash value can be established in two ways.  
The first is that the hash can be linked to pseudo-identifiers as a secondary effect that is not the object of the processing. The second case arises when the purpose of the processing is to link pseudo-identifiers to each other through a hash value.  
In one way or another, the information these provide decreases the effectiveness of hash functions by providing clues about the information contained in the hash value that will allow for the identification of the subject. The risk of re-identification will depend not only on the type of pseudo-identifiers but also on the correct application of randomization or generalization techniques on the indirect identifiers. To determine to what extent that set of information is anonymous, it would be necessary to conduct an analysis of, for example, k-anonymity.  
LINKING OTHER TYPES OF INFORMATION  
There may be additional conditions that arise when the theoretical design of a processing operation is concretized in an implementation on an ICT system and with specific work procedures. The actual operation may generate circumstances that allow for the linking of additional information to the hash, which was not foreseen in the original concept of the processing, for example:  
• The relative position of the hash in a table or data chain allows for establishing relationships between previously or subsequently stored information.  
• The date of registration of the hash in a table allows for linking it with information stored in other tables or chains that were recorded on the same date.  
• Similarly, log files associated with transmission, use of computing services, access to storage systems, etc., are sources of information that allow for cross-referencing data.  
All these possibilities must be taken into account when determining the difficulty of re-identifying the hash.

This principle is known as Uniqueness Distance26 and establishes that, above a threshold of encrypted text, both the plain text and the key are determined. This implies that, even if the key could be erased by the data controller, the key is implicitly contained in the encrypted text, so neither the key nor the information it protects disappears and, therefore, they are susceptible to being recovered27.  
Therefore, re-identification will be protected with a certain level of guarantee that will depend on the inherent weaknesses of any encryption system:  
• The commitment to the confidentiality of the key. Working in distributed environments could increase this risk28.  
• The strength in key generation.  
• Vulnerability to known plaintext or chosen plaintext attacks29.  
• The volume of encrypted information; the more information, the easier it is to cryptanalyze.  
• The principle of uniqueness distance.  
• The development of computing power and new cryptanalysis algorithms.  
• The existence of unknown weaknesses in the encryption system.

ATTACHMENT OF A HEADER TO THE MESSAGE OR SAL WITH REUSE  
Another strategy to hinder re-identification is to add a constant value or "salt" to all messages before evaluating the hash. A salt is a random value that is added to the original message. If it is random, it must be independent of the same message or any other information.  
The format of the message changes, as the salt field must be added to the original message. The new expanded message will have the following form:  

Let us assume we are dealing with the hashing of phone numbers. With this new strategy, the message space of the processing would not consist solely of phone numbers, but rather of the pair "salt+phone number." For example, before calculating the hash of the number "+34654323211," a pre-calculated random value would be added to the message: "112358314…+3465323211." Once the expanded message has been created, the hash is calculated. To verify the hash for any message, one only needs to add the salt stored in the system to the original message. If, due to a collision, the hash of a phone number matches a stored hash, that match does not validate the number, as isolated numbers are not part of the expanded message space.  
As in the case of using a key, the value of the salt must remain secret, and the amount of information in the message space remains constant, neither increasing nor decreasing. The process can be graphically represented as follows:  

If the value of the salt is removed by the data controller, the information does not disappear, but its access will be protected with a certain level of guarantee, as an approximation to the principle of uniqueness distance is fulfilled, as in the case of encryption. Although the hash algorithm is not inherently reversible, the situation in which the message space is found in relation to the salt+messages space is similar to what occurs with the encryption model. Moreover, the salt is also implicitly found in the generated hash space.  
Additionally, re-identification will be protected with a certain level of guarantee that will depend on the weaknesses of the system, among others:  
• The commitment to the confidentiality of the unique salt used, whose control is more difficult in distributed environments.  
• The properties of the salt, which will depend on its length and the randomness of the salt generation system. A shorter salt will be vulnerable to brute force attacks and Rainbow Tables. A salt value generation system with weaknesses may infer that it takes a value within a limited set of options.  
• The level of development of computing power and new hash-breaking algorithms, which necessitate the generation of increasingly longer salts.  
• The existence of unknown weaknesses in the hash algorithm or in the processing system.  
MODELS OF SINGLE-USE SALT  
The use of single-use salt allows for the development of models in which the risk of re-identification of the hash is reduced. In the event that such salt is removed, the original message, provided that certain guarantees are met, could be considered anonymized.  
Single-use salt entails generating a distinct random element for each of the messages. This random element must be completely independent of any message and of any other salt generated for another message.  
A didactic example of this model could be as follows:  
First, the format of the original message is expanded to an expanded message consisting of three fields:  
• The message itself.  
• An additional salt that we will call nonce, whose purpose is to increase the entropy of the message to a value approximately equal to the number of output bits of the hash function. Of course, this nonce value must be generated randomly, must be independent of the message, and independent of any other nonce value, that is, also single-use.  
• A single-use salt value, independent of the two previous ones and of any other salt value. That is, also single-use.  
The format of the expanded message for processing would be as follows:  

A very simplified example, which does not take into account block chaining: assuming a hash algorithm A that works with blocks of size k and uses a salt S, of size n=k. The attacker knows or manages to calculate the hash H of a message M of size k: A(S || M) = H. By working in blocks, I know that A(S)+A(M) = H. Therefore, A(S) = H-A(M). Knowing the hash of S, I can develop a Rainbow Table attack or other strategies to obtain an equivalent salt.  
In particular, due to Bitcoin mining, which consists of obtaining hash values with certain characteristics, significant development is being made in optimizing the speed of the SHA256 algorithm.  
See the section related to hash analysis as a pseudonymization system in this document.  
Nonce is an arbitrary number, typically generated randomly, that can only be used in the encryption scheme once.
Page: 19 of 31

A valid message in the message space of the processing should have the previous structure, which we will call an expanded message. The expanded message is stored by the responsible party, and the salt and nonce fields are kept confidential for each of those messages. This strategy would have the following effects:
• On one hand, by adding a nonce to each possible message that expands the entropy of the message space, a message space on the order of the hash space would be obtained, making a homogeneous coverage of the latter highly probable. That is, there is a high likelihood that every possible hash value could correspond to a valid message.

• On the other hand, since the salt is single-use and not shared, the space of possible (salt+nonce+messages) grows in such a way that each hash value has a high probability of corresponding to as many (salt+nonce+message) triples as there are hash values. That is, the possibility of collision is guaranteed.

The characteristics that this model would have are as follows:
• To compromise re-identification, access to the salt and nonce value associated with each message is required.
• The possibility of collision in the expanded message space is guaranteed, since for the same message there is a high probability that all messages from the original space could have the same hashes if the appropriate salt and nonce are selected.
• The hash value does not identify a single expanded message within the space of possible expanded messages, although the current state of technology makes it very difficult to construct an expanded message (salt+nonce+false message) that has the same hash as that generated from the expanded message (salt+nonce+true message). Therefore, it fulfills its function as a unique identifier. For this, the length of the salt+nonce must be sufficiently large.
• On the other hand, the entity that possesses the trio (salt+nonce+message) can validate the hash.
In the event that such an expanded message is deleted by the responsible party, that is, the message is removed, but also the salt and nonce associated with that specific message, it is not possible to validate the hash at first instance. By using random information that is single-use, and if there is no linkage between the salts of the different hashes, re-identification is made more difficult. If the salt is sufficiently large, and the original salt has been deleted, for any message a salt could be constructed that would validate the hash (as long as there is no additional linked information), which would weaken the association of the hash with the original message.

DIFFERENTIAL MODELS
In the same line as the previous model, and with the same precautions and conclusions, is the application of differential privacy models.
In this case, the strategy consists of adding a noise value to the message that, unlike a salt that is included as a header of the message, is incorporated into the message itself. This noise value can be applied in many ways to both graphical, sound, or other types of scalar data, using differential privacy techniques to design and implement them, such as those used in digital watermarks.

For the noise value to be considered acceptable, it would be necessary for it to meet certain conditions. First, it is essential to analyze its random nature and its disconnection from the content of the message. On the other hand, it would be necessary to ensure the non-correlation of the introduced noise between different messages, in addition to ensuring that it adds entropy well above the number of bits of the hash result, and finally, it must be verified that the state of technology does not allow processing models that enable re-identification.

One of the advantages of these models over the previous single-use salt model is the elimination of the vulnerability associated with block processing in the implementation of most hash algorithms.

• Use of one-time salt/random values.  
• If applicable, the size of a salt value above the hash block size, without being a multiple of the block size.  
• Use appropriate random information generators for cryptographic techniques.  
• Secure access to the hash execution process.  
• No linkage with identifiers, pseudonyms, or other information, particularly within the same record and between records or parallel tables/chains.

3.8 SELECTION OF ANONYMIZATION TECHNIQUES: KEYS  
1. HASH ALGORITHMS: The utility of encryption algorithms when we need to anonymize microdata is unquestionable, with "hash" algorithms being particularly useful. A hash algorithm is a mechanism that, when applied to a specific piece of data, generates a unique or almost unique key that can be used to represent that data. For example, we have a piece of data that we want to hide or anonymize, and for this, we use a hash algorithm, such as SHA1 or MD5. From the application of the algorithm to a specific piece of data, we obtain a key or digital fingerprint that can be used to replace the actual data. The hash algorithm generates a digital fingerprint and makes it impossible to reconstruct the original data from the fingerprint, and on the other hand, any variation in the original data will result in a different digital fingerprint, which, expressed in computational terms, could be said that modifying a single bit in the original information stored on a computer would result in a different key or a different digital fingerprint.
Page: 28 of 31  
The hash algorithm allows us to generate the same digital fingerprint from the same data or microdata, but starting from a specific digital fingerprint, we will never be able to obtain the original data, ensuring confidentiality as it is a one-way mathematical operation. The keys resulting from the application of a hash algorithm are commonly known as "digital fingerprints" because they are understood to uniquely represent a specific data or microdata.  
However, a hash algorithm alone is not sufficient to make anonymization irreversible, as small text strings, such as the microdata corresponding to a person's postal code, a phone number, etc., can be easily reidentified with a computer program that generates consecutive numbers and their corresponding digital fingerprints. If what we want is to guarantee the anonymization of a microdata, it is necessary to use a cryptographic mechanism that ensures the secrecy of the digital fingerprint we have generated. A good option is the HMAC algorithm based on RFC2014. HMAC can be used in combination with various hash algorithms, such as MD5, and applies a cryptographic algorithm to the resulting digital fingerprint or key from the hash algorithm, generating a new digital fingerprint or key based on a secret key.  
The use of HMAC in combination with non-trivial secret keys and a diligent key destruction policy can help ensure the irreversibility of the anonymization process. When the keys used with HMAC are retained, they can be used to generate pseudonymized data that require subsequent reidentification of the data subjects. Secret key hashing mechanisms can be useful for masking data. However, there must be a procedure that allows for the secure deletion of the keys and the possibility of proving that the procedure has been followed to guarantee the irreversibility of the process.

Hashing without key  
Hashing is a technique that can be used to derive pseudonyms, but, as will be shown later in this Section, has some serious drawbacks with regard to the design goals set in Section 3.1. Still, it is a starting point for understanding other stronger techniques in the field and this is why we present it first. Moreover, hashing can be a useful tool to support data accuracy. A cryptographic hash function h is a function with specific properties (as described next) which transforms any input message m of arbitrary length to a fixed-size output h(m) (e.g. of size 256 bits, that is 32 characters), being called hash value or message digest. The message digest satisfies the following properties [Menezes, 1996]:  
i) given h(m), it is computationally infeasible to compute the unknown m, and this holds for any output h(m) - i.e. the function h is mathematically irreversible (pre-image resistance),  
ii) for any given m, it is computationally infeasible to find another m’≠ m such that h(m’)=h(m) (2nd pre-image resistance),
Page: 29 of 31  
iii)  
it is computationally infeasible to find any two distinct inputs m, m’ (free choice) such that h(m’)=h(m) (collision resistance). Clearly, if a function is collision-resistant, then it is 2nd pre-image resistant too.  
In other words, a cryptographic hash algorithm is one that generates a unique digest (which is also usually called fingerprint) of a fixed size for any single block of data of arbitrary size (e.g. an initial identifier of any kind). Note that for any given hash function, the same unique digest is always produced for the same input (same block of data). It is important to point out that state-of-the-art hash functions should be chosen; therefore, commonly used hash functions such as MD5 and SHA-1 [Menezes,1996] with known vulnerabilities – with respect to the probability of finding collisions - should be avoided (see [Wang, 2005], [Dougherty,2008], [Stevens, 2017a], [Stevens,2017b]). Instead, cryptographically resistant hash functions should be preferable, e.g. SHA-2 and SHA-3 are currently considered as state-of-the-art [FIPS, 2012], [FIPS,2015].  
The above properties of hash functions allow them to be used in several applications, including data integrity and entity authentication. For instance, once an app market has a hash server storing hash values of app source codes, any user can verify whether the source code has been modified or not via a simple validation of its hash value - since any modification of the code would lead to a different hash value (see, e.g., [Jeun, 2011]). Similarly, recalling the discussion in Section 3.1 on data accuracy, a pseudonym that is generated via hashing user’s identifiers may be a convenient way for a data controller to verify a user’s identity. However, when it comes to pseudonymisation, despite the aforementioned properties of a cryptographic hash function, simple hashing of data subjects’ identifiers to provide pseudonyms has major drawbacks. More precisely, with regard to the aforementioned D1 and D2 design goals, we have the following:  
• The D2 property does not hold, since any third party that applies the same hash function to the same identifier gets the same pseudonym.  
• In relation to the above observation, the D1 property also does not necessarily hold, since it is trivial for any third party to check, for a given identifier, whether a pseudonym corresponds to this identifier (i.e. through hashing the identifier).  
Therefore, a reversal of pseudonymisation is possible whenever such an approach is adopted, as having a list of the (possible) initial identifiers is adequate for any third party to associate these identifiers with the corresponding pseudonyms, with no other association being in place. In fact, following the GDPR definition of pseudonymisation, one could argue that hashing is a weak pseudonymisation technique as it can be reversed without the use of additional information. Relevant examples are provided in [Demir, 2018] (and in references therein), where the researchers refer to the Gravatar service and describe how users’ email addresses can be derived through their hash value, which is shown in the URL that corresponds to the gravatar of the user, without any additional information.  
Hence, hash functions are generally not recommended for pseudonymisation of personal data, although they can still contribute to enhancing security in specific contexts with negligible privacy risks and when the initial identifiers cannot be guessed or easily inferred by a third party. For the vast majority of cases, such pseudonymisation technique does not seem to be sufficient as a data protection mechanism [Demir, 2018]. However, a simple hashing procedure may still have its own importance in terms of data accuracy, as stated previously.  
Hashing with key or salt
Page: 30 of 31  
A robust approach to generate pseudonyms is based on the use of keyed hash functions – i.e. hash functions whose output depends not only on the input but on a secret key too; in cryptography, such primitives are being called message authentication codes (see, e.g., [Menezes, 1996]). The main difference from the conventional hash functions is that, for the same input (a data subject’s identifier), several different pseudonyms can be produced, according to the choice of the specific key – and, thus, the D2 property is ensured. Moreover, the D1 property also holds, as long as any third party, i.e. other than the controller or the processor, (e.g. an adversary) does not have knowledge of the key and, thus, is not in the position to verify whether a pseudonym corresponds to a specific known identifier. Apparently, if the data controller needs to assign the same pseudonym to the same individual, then the same secret key should be used. To ensure the aforementioned properties, a secure keyed-hash function, with properly chosen parameters, is needed. A known such standard is the HMAC [FIPS, 2008], whose strength is contingent on the strength of the underlying simple hash function (and, thus, incorporating SHA-2 or SHA-3 in HMAC is currently a right option). Moreover, the secret key needs to be unpredictable and of sufficient length, e.g. 256 bits, which could be considered as adequate even for the post-quantum era. If the secret key is disclosed to a third party, then the keyed hash function actually becomes a conventional hash function in terms of evaluating its pseudonymisation strength. Hence, recalling the definition of pseudonymisation in the GDPR, the data controller should keep the secret key securely stored separately from other data, as it constitutes the additional information, i.e. it provides the means for associating the individuals – i.e. the original identifiers – with the derived pseudonyms.  
Keyed hash functions are especially applicable as pseudonymisation techniques in cases that a data controller needs - in specific data processing context - to track the individuals without, however, storing their initial identifiers (see also [Digital Summit, 2017]). Indeed, if the data controller applies - always with the same secret key - a keyed hash function on a data subject’s identifier to produce a pseudonym, without though storing the initial user’s identifier, then we have the following outcomes:  
• The same pseudonym will always be computed for each data subject (i.e. allowing tracking of the data subject).  
• Associating a pseudonym to the initial identifier is practically not feasible (provided that the controller does not have knowledge of the initial identifiers).  
Therefore, if only tracking of data subjects is required, the controller needs to have access to the key but does not need to have access to the initial identifiers, after pseudonymisation has been performed. This is an important consideration that adheres to the principle of data minimization and should be considered by the controller as a data protection by design aspect. Moreover, a keyed hash function has also the following property: if the secret key is securely destroyed and the hash function is cryptographically strong, it is computationally hard, even for the data controller, to reverse the pseudonym to the initial identifier, even if the controller has knowledge of the initial identifiers. Therefore, the usage of a keyed hash function may allow for subsequent anonymisation of data, if necessary, since deleting the secret key actually deletes any association between the pseudonyms and the initial identifiers. More generally, using a keyed hash function to generate a pseudonym and subsequently deleting the secret key is somehow equivalent to generating random pseudonyms, without any connection with the initial identifiers.

Another approach that is often presented as an alternative to the keyed hash function is the usage of an unkeyed (i.e. conventional) hash function with a so-called “salt” – that is the input to the hash function is being augmented via adding auxiliary random-looking data that are being called “salt”. Again, if such a technique is appropriately applied, for the same identifier, several different pseudonyms can be produced, according to the choice of the salt – and, thus, the D2 property is ensured, whilst the D1 property also holds with regard to third parties provided that they do not have knowledge of the salt. Of course, this conclusion is valid only as long as the salt is appropriately secured and separated from the hash. Note that, as in the case of keyed hash, the same salt should be used by the controller in cases that there is need to assign always the same pseudonym to the same individual. Moreover, salted hash functions can be utilized in cases where the controller does need to store the initial identifiers, while still being able to track the data subjects. Last, if the salt is securely destroyed by the controller, it is not trivial to restore the association between pseudonyms and identifiers.  
However, it should be stressed that in several typical cases employing salts for protecting hashes has some serious drawbacks:  
On one hand, the salt does not share the same unpredictability properties as secret keys (e.g. a salt may consist of 8 characters, i.e. 64 bits, as in the cases of protecting users’ passwords in some Linux systems). More generally, from a cryptographic point of view, a keyed hash function is considered as a more powerful approach than a salted hash function. There exist though several cryptographically strong techniques for generating salted hashes, which in turn could be considered as appropriate candidates for generating pseudonyms – a notable example being the bcrypt [Provos, 1999].
